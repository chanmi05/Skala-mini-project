# HWP를 RAG 청킹 입력 데이터로 만드는 전처리 절차

## 1. 목적과 범위

HWP 파일을 받아 문서 구조와 출처를 유지한 **조항 단위 JSON/JSONL**로 변환한다.
이 결과를 청킹 모듈에 직접 전달한다. PDF 로더를 거치거나 PDF로 변환할 필요는 없다.

이번 작업의 수집 대상은 `표준취업규칙_2026` 문서의 **왼쪽 ‘취업규칙(안)’ 열**이다.
오른쪽 ‘작성시 착안사항’은 검색 본문에서 제외한다.
일반 근로자용과 단시간 근로자용 규정은 별도로 구분한다.

전처리는 원래 문서의 논리적 단위를 복원하는 작업이다. 조항 길이에 따라 검색용
청크를 나누고, 임베딩하거나 벡터 DB에 저장하는 작업은 이 문서의 수행 범위 밖이다.

| 구분 | 수행 내용 | 결과 |
|---|---|---|
| 구조 추출 | 문단·표·셀과 원문 위치 읽기 | 구조 데이터 |
| 선택·전처리 | 왼쪽 열 선택, 적용 대상 구분, 조항 복원 | 조항 데이터 |
| 청킹 | 조항을 유지하거나 긴 조항만 항·호 경계에서 분할 | 검색용 청크 |
| 색인 | 청크를 Document로 변환하고 임베딩·저장 | 검색 저장소 |

## 2. 전체 흐름

```text
HWP 수신 및 검사
    ↓
원본 보관·문서 ID 부여
    ↓
XML 기반 문단·표 구조 추출
    ↓
문서 영역과 적용 대상 구분
    ↓
규정안/작성 지침 비교표 식별
    ↓
왼쪽 규정안 열 선택
    ↓
문단 정리·중첩 표 연결
    ↓
장·절·조·항·호 구조 복원
    ↓
기본 문안·대체 문안·예시 구분
    ↓
품질 검사
    ├─ 통과 → 조항 JSONL → 청킹 모듈
    └─ 실패 → 재처리 또는 검토 대기
```

## 3. 단계별 수행 방법

### 3.1 파일 수신 및 검사

1. 확장자와 실제 파일 형식을 확인한다. HWP 5와 HWPX는 추출 경로를 분리한다.
2. 암호화·손상·지원하지 않는 형식 등 읽기 실패 원인을 기록한다.
3. 원본 파일의 SHA-256 해시를 계산한다.
4. 원본, 파일명, 해시, 수집 시각, 전처리 정책 버전을 저장한다.

중복 처리는 파일 해시와 정책 버전을 함께 기준으로 판단한다. 같은 파일이라도
선택·정규화 규칙이 변경되면 재처리가 필요하다. 실패한 파일을 빈 문서로 성공 처리하지 않는다.

### 3.2 문단·표 구조 추출

이번 파일은 `pyhwp`의 XML 출력을 사용한다. `olefile`은 내부 스트림을 읽는
저수준 도구이며, 이것만으로 조항·표 의미가 자동 복원되는 것은 아니다.

추출 시 다음을 보존한다.

- 문단 텍스트와 원문 내부 순서
- 표 ID, 행·열 좌표, 셀 병합 범위
- 중첩 표와 부모 셀의 관계
- 문단 ID와 XML 경로 등 원문 위치
- 이미지·수식 등 텍스트 외 콘텐츠의 존재 여부와 위치(추가 구현 대상)

서식 때문에 나뉜 텍스트 조각은 같은 문단 안에서 연결한다. 중첩 표의 텍스트는
부모 문단과 자식 문단에 중복 포함하지 않는다. XML 순서가 화면의 읽기 순서와
일치한다고 가정하지 말고, 표에서는 행·열 좌표와 병합 정보를 함께 사용한다.

TXT는 사람이 확인하는 보조 산출물로 사용하고 구조 데이터의 대체재로 삼지 않는다.
추출 실패나 누락이 의심되면 파서 진단, 다른 추출 경로, 필요 시 HWPX 변환 등을
검토하고 원본과 비교한다. OCR은 이미지 콘텐츠가 필요한 경우에 별도 적용한다.

### 3.3 문서 영역과 적용 대상 구분

원문 제목과 문단·표의 위치를 사용해 다음 영역을 구분한다.

| 항목 | 처리 정책 |
|---|---|
| 일반 근로자용 규정 본문 | `worker_type=general`로 수집 |
| 단시간 근로자용 규정 본문 | `worker_type=part_time`으로 수집 |
| 목차 | 구조 확인용으로 보관하고 규정 본문에서는 제외 |
| 별첨·별도 규정 | 별도 영역으로 보관하고 이번 본문 수집에서는 제외 |
| 계약서·통지서 등 양식 | 별도 유형으로 보관하고 이번 본문 수집에서는 제외 |

조항 키는 `문서 ID + 적용 대상 + 규정 영역 + 조 번호 + 문안 식별자`로 만든다.
`제1조`처럼 조 번호만으로 식별하면 적용 대상이나 별첨의 조항이 충돌할 수 있다.
같은 문구라도 적용 대상이 다르면 문자열 중복이라는 이유만으로 제거하지 않는다.

### 3.4 대상 비교표 식별 및 왼쪽 열 선택

표의 머리글과 구조를 확인해 다음 조건에 맞는 비교표를 찾는다.

- 왼쪽 머리글: `취업규칙(안)`
- 오른쪽 머리글: `작성시 착안사항` 또는 괄호·공백을 포함한 동등한 표기
- 구조: 규정안과 작성 지침이 좌우로 대응하는 표

머리글 비교에 사용할 문자열만 공백·괄호 등을 정규화하고, 본문 원문은 그대로 보관한다.
머리글이 병합되어 있거나 반복·누락되었으면 구조를 확인하고 판별 근거를 기록한다.
판별이 불명확하면 임의로 첫 번째 열을 고르지 않고 검토 대상으로 남긴다.

정책의 개념 예시는 다음과 같다. 아래 설정을 실행하는 정책 엔진은 아직 구현되어 있지 않다.

```yaml
policy_id: employment_rules_left_column_v1
target:
  table_type: regulation_guidance_comparison
  normalized_headers:
    left: 취업규칙안
    right: 작성시착안사항
selection:
  include: left_column
  include_nested_content: true
  exclude: right_column
unmatched_action: review
```

**열 선택은 대상 바깥 비교표에만 적용한다.** 왼쪽 셀에 있는 중첩 표는 모든 필요한
열을 유지한다. 중첩 표에 ‘왼쪽만 선택’을 재귀 적용하면 내용이 훼손될 수 있다.
왼쪽 셀의 행·열 위치와 원문 경로를 함께 남기고 오른쪽은 원본 구조 데이터에 보관한다.

### 3.5 텍스트 정리 및 중첩 콘텐츠 처리

원문 텍스트와 정규화된 텍스트를 구분하거나, 변경 내역을 기록해 정규화 결과를
추적할 수 있도록 한다. 번호·조건·단위가 바뀌는 정규화는 허용하지 않는다.

| 대상 | 처리 방법 |
|---|---|
| 불필요한 제어문자 | 의미와 위치를 확인한 뒤 정리 |
| 서식 때문에 분리된 문단 내 텍스트 | 원문 순서대로 연결 |
| 문단 내부의 시각적 줄바꿈 | 문장·항목 경계를 확인한 뒤 연결 |
| 반복 머리말·꼬리말·페이지 표시 | 반복 위치 등 근거가 확인된 경우에만 제외 |
| 조·항·호 번호, 단서, 예외 | 보존 |
| 숫자, 기간, 단위, 부정 표현, 법령명 | 보존 |
| `○○`, 미기입 날짜, 빈칸 | 표준 문안의 자리표시자로 보존 |
| 중첩 표 | 별도 객체로 보존하고 본문 위치에서 참조 |
| 수식·그림·분수 형태 표 | 누락 여부를 기록하고 해석이 필요하면 검토 |

중첩 표는 본문에 한 번만 나타나도록 소유 관계를 정한다. 표를 부모 셀 텍스트에
펼쳐 넣는 방식과 별도 표 객체로 저장하는 방식을 동시에 중복 적용하지 않는다.
본문에는 `table_ref`를 두고 별도 표 객체에 셀 구조를 보관하는 방식을 권장한다.

### 3.6 장·절·조·항·호 구조 복원

왼쪽 셀을 순서대로 읽는 동안 현재 적용 대상, 영역, 장, 절, 조항을 상태로 유지한다.

1. 장·절 제목을 만나면 현재 상위 문맥을 갱신한다.
2. 조항 제목을 만나면 새 조항을 시작한다.
3. 조항 제목이 없는 후속 문단은 현재 조항의 연속 여부를 확인해 연결한다.
4. 항·호는 상위 조항 안에서 구조화하고 순서를 보존한다.
5. 적용 대상·영역 전환 시 현재 상태를 종료한다. 다른 영역으로 조항을 이어 붙이지 않는다.
6. 조항에 편입되지 않은 문단도 기록한다. 장 제목·부칙 등은 별도 유형으로 보존하고,
   분류할 수 없는 내용은 검토 대상으로 남긴다.

조항 제목 후보를 찾는 정규식 예시:

```python
# 후보 탐지용이다. 이것만으로 조항 경계를 확정하지 않는다.
article_pattern = r"^\s*제\s*\d+\s*조(?:\s*의\s*\d+)?\s*[（(]"
```

문단 시작, 제목 괄호, 주변 구조 등을 함께 확인한다. 본문 속 ‘제6조에 따라’를
새 조항으로 인식해서는 안 된다. 제목 없는 조항, 한 문단의 여러 제목, `제○조`
예시 등도 있을 수 있으므로 후보 탐지 실패를 조용히 무시하지 않는다.

**한 셀에 여러 조항이 있으면 분리하고, 여러 셀에 걸친 조항은 연결한다.**
셀 경계는 출처 정보이며 논리적 조항 경계가 아니다.

### 3.7 기본 문안·대체 문안·예시 구분

왼쪽 열이라도 모든 내용이 하나의 기본 규정은 아니다. 다음 유형을 구분한다.

| 유형 | 보관 방법 |
|---|---|
| 기본 규정안 | `content_type=rule_template` |
| 특정 조건의 대체 문안 | `content_type=alternative_template`, 적용 조건·기본 조항 연결 |
| 참고·예시 | `content_type=example`, 관련 조항 연결 |
| 판별 불가 | 검토 사유와 원문을 보존하고 자동 청킹 전달 보류 |

‘상시 30명 이하의 사업’, ‘퇴직금 제도를 운영하는 경우’ 같은 조건은 문안과 함께
보존한다. 대체 문안이 기본 조항과 같은 번호를 쓰더라도 덮어쓰지 않는다.
표준취업규칙은 표준 문안이므로 특정 회사에 실제 시행 중인 규정으로 표시하지 않는다.

## 4. 자동화 로직 구성

공통 추출기와 문서별 선택 정책을 분리한다. 모든 HWP가 같은 표 구조를 갖는다고
가정하지 않는다. 이번 문서의 정책에 매칭되지 않는 파일은 다른 정책으로 분기하거나
검토 대기 상태로 보낸다.

다음은 구현 순서를 보여주는 의사 코드이며, 현재 존재하는 함수 목록은 아니다.

```python
manifest = inspect_and_register(source_file, policy_version)
structure = extract_structure(source_file)
regions = classify_regions(structure)
selected = select_regulation_cells(regions, policy)
normalized = normalize_preserving_provenance(selected)
articles, unassigned = reconstruct_articles(normalized)
articles = classify_variants(articles)
report = validate(manifest, selected, articles, unassigned)

save_intermediate_outputs(manifest, structure, selected, articles, report)
if report.ready_for_chunking:
    export_articles_jsonl(articles)
else:
    enqueue_review(report)
```

먼저 규칙으로 명확하게 처리할 수 있는 부분을 구현한다. LLM을 추가하는 경우
불명확한 영역·문안의 분류 보조에 한정하고 원문 변경이나 모호한 내용의 보완에는 사용하지 않는다.
분류 결과는 원본 블록 ID에 연결하고 검증할 수 없는 판정을 확정된 결과로 취급하지 않는다.

## 5. 청킹 입력용 데이터 명세

주요 출력은 한 줄에 한 레코드를 저장하는 `articles.jsonl`로 한다. 다음은 형식 예시이며
실제 파일에서 인용한 내용은 아니다.

```json
{
  "document_id": "employment_rules_2026",
  "preprocessing_version": "left_column_v1",
  "article_id": "employment_rules_2026_general_main_art6_default",
  "worker_type": "general",
  "section_type": "main_rules",
  "chapter": {"number": "제2장", "title": "채용 및 근로계약"},
  "section": null,
  "article_number": "제6조",
  "article_title": "근로계약",
  "content_type": "rule_template",
  "variant_id": "default",
  "applies_when": null,
  "content": [
    {
      "type": "paragraph",
      "number": "①",
      "text": "해당 항의 원문",
      "source_spans": [
        {"block_id": "p100", "start": 0, "end": 9}
      ]
    },
    {"type": "table_ref", "table_id": "nested_table_1"}
  ],
  "source_cells": [
    {"table_id": "5", "row": 8, "column": 0}
  ],
  "review_flags": [],
  "ready_for_chunking": true
}
```

`source_spans`의 오프셋은 지정한 원본 블록 텍스트의 문자 위치이며 시작 포함·끝 제외로
정의한다. 실제 구현 시 범위와 원문 일치 여부를 검사한다. 본문 `content`는 문단과
표 참조가 등장하는 순서를 유지한다. 별도 `tables.json`에 참조된 표 구조를 보관한다.
페이지 번호는 검증된 매핑이 있을 때만 추가한다.

조항 외 제목·부칙 등은 `supplementary_blocks.jsonl` 등에 별도 보관한다. 조 번호가
없다는 이유만으로 버리거나 직전 조항에 강제로 붙이지 않는다.

## 6. 품질 검사 및 완료 조건

| 검사 항목 | 수행 방법 | 이상 시 처리 |
|---|---|---|
| 추출 성공 | 본문 존재, 파서 오류, 비텍스트 콘텐츠 확인 | 실패 사유 기록·재처리 |
| 대상 표 선택 | 머리글·주변 제목·적용 대상 확인 | 정책 미매칭 검토 |
| 선택 본문 보존 | 선택 블록이 조항·보조 데이터·명시적 제외 사유 중 하나로 추적되는지 확인 | 누락·중복 조사 |
| 오른쪽 열 제외 | 본문의 출처가 선택한 왼쪽 셀 하위인지 확인 | 출처 연결 수정 |
| 조항 구조 | 동일 영역의 번호 중복·역전·누락 후보 확인 | 대체 문안·원문 번호와 대조 |
| 중첩 표 | 참조 대상 존재, 중복 편입 여부 확인 | 표 소유 관계 수정 |
| 출처 | 블록 ID·경로·문자 범위 유효성 확인 | 전달 보류 |
| 원본 대조 | 최초 정책 적용 시 대표 조항, 여러 조항 셀, 셀 간 연속 조항, 중첩 표, 대체 문안 비교 | 규칙 보완 |

조 번호의 누락·중복은 오류 후보이지 무조건 오류는 아니다. 원문과 정책을 확인해
판단하고, 불확실한 항목은 `review_flags`에 남긴다. 정규화 때문에 글자 수가 달라질
수 있으므로 전체 글자 수 비교만으로 보존 여부를 판정하지 않는다.

문서 단위의 준비 상태를 관리한다. 기본적으로 필수 검사와 검토가 끝난 문서만
청킹 모듈로 전달한다. 부분 전달이 필요하면 제외된 범위와 미해결 항목을 명시하는
별도 정책을 둔다.

## 7. 현재 프로젝트에서 실행할 수 있는 부분

프로젝트 루트에서 다음을 실행하면 현재 구조 추출 결과를 재생성할 수 있다.

```bash
cd parse-hwp
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python extract.py Standard_Rules_of_Employment_2026.hwp
```

현재 구현의 실행 환경과 의존성 호환성은 [README](README.md)에 기록되어 있다.

| 현재 파일 | 활용 방법 |
|---|---|
| `extract.py` | pyhwp 기반 구조 추출 실행 |
| `output/*.xml` | 원본 구조 진단 |
| `output/*.blocks.jsonl` | 문단 ID·텍스트·중첩 셀 위치 추적 |
| `output/*.tables.json` | 표·병합 셀·중첩 표 확인 |
| `output/*.paired_rows.jsonl` | `regulation_template`을 왼쪽 본문 입력으로 사용 |
| `output/*.report.json` | 추출 통계와 한계 확인 |

현재 파일에서는 표 ID `5`가 일반 근로자용, `27`이 단시간 근로자용 본문이다.
이는 분석으로 확인한 이 파일의 값이며 새 문서 처리 규칙에 하드코딩하지 않는다.

`paired_rows.jsonl`은 빠른 실험의 출발점이다. 다만 셀 텍스트가 합쳐져 있으므로
정밀한 문단 위치, 중첩 표 연결과 중복 방지는 blocks/tables 데이터를 함께 사용해야 한다.

현재 완료된 작업은 구조 추출과 규정안/지침 행 분리다. 범용 적용 대상 판별,
왼쪽 본문 조항 복원, 문안 분류, 위 품질 검사와 `articles.jsonl` 생성은 추가 구현 대상이다.

## 8. 청킹 모듈 및 기존 RAG 코드와 연결

전처리의 산출물인 `articles.jsonl`을 직접 읽는다. PDF 로더에 다시 넣지 않는다.

```text
articles.jsonl + 연결된 표
    ↓
조항별 청킹(긴 조항만 항·호 경계 분할)
    ↓
LangChain Document 목록
    ↓
기존 임베딩·FAISS 저장
```

청킹에서는 적용 대상·장·절·조 제목과 부모 조항 ID를 각 청크에 유지한다.
문서 단위 글자 수 분할을 다시 일괄 적용해 복원한 조항 경계를 무너뜨리지 않는다.
긴 조항의 크기 기준과 검색 품질 평가는 전처리 이후 별도로 결정한다.
