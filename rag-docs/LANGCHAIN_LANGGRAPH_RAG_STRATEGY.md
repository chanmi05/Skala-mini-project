# LangChain·LangGraph 기반 RAG 개발 전략

작성일: 2026-10-23 (Asia/Seoul)  
상태: 최초 설계 문서. 이후 기본 라우터·문서 그래프를 구현했다.
실제 구현 범위와 미구현 항목은 [구현·State 초안](RAG_ROUTER_WORKFLOW_USAGE.md)을 참고한다.

## 1. 목표와 담당 범위

문서 종류가 바뀌더라도 입력 상황, 근거 부족, 재검색, 답변 유보를 일관되게 처리한다.
특정 논문의 실패 질문을 해결하기 위한 단어·정답을 코드에 하드코딩하지 않는다.

- 입력: 사용자 질문, 필요한 범위의 대화 이력, 문서 저장소, 모델, 실행 설정.
- 출력: 답변 또는 확인 질문, 처리 상태, 실제 사용 근거, 실행 횟수·지연.
- 제외: 원본 수집·추출·전처리·청킹, 임베딩 적재, STT·TTS 구현.
- 원칙: 기존 서버·API와 `rag_agent.py`를 보존하고 별도 모듈로 구현·검증한 뒤 연결.

검색 대상은 PDF에서 만들어진 문서 저장소 하나다. 웹 검색이나 네이버 연동은 추가하지 않는다.
실제 저장소·메타데이터·임베딩 적재의 담당 경계는 데이터 파이프 담당자와 확정한다.

## 2. 채택할 구조

LangChain은 입력 분석·구조화된 판정·분기를 구성하고, LangGraph는 문서 질문의 상태와
제한된 검색 반복을 관리한다. 자율적인 도구 선택을 무제한 허용하는 Agent 대신
실행 경로와 횟수를 명시한 워크플로로 시작한다.

```text
질문 + 대화 이력
    ↓
기본 검증(Python)
    ↓
입력 분석(LangChain: 프롬프트 + 구조화 출력)
    ↓
분기(LangChain RunnableBranch)
    ├─ 인사 → 안내
    ├─ 의미 불명확 → 확인 질문
    ├─ 명확한 범위 밖 요청 → 범위 안내
    └─ 문서 질문 → LangGraph
                      검색용 질문 준비
                            ↓
                          검색 ←──────────────┐
                            ↓                 │
                       컨텍스트 구성          │
                            ↓                 │
                       근거 충분성 확인       │
                        ├─ 충분 → 답변 생성 → 종료
                        ├─ 조건 불명확 → 확인 질문 → 종료
                        ├─ 재검색 가능 → 질문 재구성 ─┘
                        └─ 한도 도달·진전 없음 → 유보 → 종료
```

빈 입력은 LLM이나 그래프에 보내지 않는다. 외부 서비스 장애는 별도 오류 경로로 종료한다.

## 3. 입력 유형과 정책

| 상황 | 예시 | 정책 |
|---|---|---|
| 빈 입력 | 빈 문자열·공백 | 검증 오류. 검색·모델 호출 없음 |
| 인사만 있음 | 안녕하세요 | 고정 안내 또는 짧은 인사. 검색 없음 |
| 인사와 질문이 함께 있음 | 안녕하세요, 휴가 조건은요? | 문서 질문으로 처리 |
| 짧고 주제가 있음 | 연차? | 길이만으로 거부하지 않음. 검색 또는 필요한 범위 확인 |
| 대상이 전혀 불명확 | 어떻게 해? | 이력으로 복원할 수 없으면 확인 질문 |
| 후속 질문 | 그럼 신청은? | 이력에서 대상이 확인되면 문서 검색으로 진행 |
| 구체적 문서 질문 | 육아휴직 신청 조건은? | 그래프로 전달 |
| 명백히 문서 범위 밖 | 지원 범위와 무관한 요청 | 범위 안내. 지원 범위가 확인된 경우만 판정 |
| 분류 불확실 | 판정이 흔들리는 입력 | 확인 질문 또는 보수적 문서 검색, 자동 차단 금지 |

입력 검증은 규칙으로 수행한다. 의미 판단이 필요한 입력에 모델 분류를 사용한다.
순수 인사 규칙을 사용한다면 전체 입력을 확인하고, 인사 단어가 있다는 이유만으로
뒤에 있는 질문을 버리지 않는다. 길이·특수문자만으로 의미 없음이라고 확정하지 않는다.

모델이 잘못 분류할 수 있으므로 의도 분류의 정답률과 과도한 확인 질문 비율도 평가한다.
문서 범위가 정해지지 않은 현재는 범위 밖 판정을 적극적으로 사용하지 않는다.

## 4. LangChain 구현 방향

| 구성요소 | 역할 |
|---|---|
| 일반 Python 검증 함수 | 공백, 길이, 검색 개수, 설정 검증 |
| `ChatPromptTemplate` | 의도 분류·검색용 질문 재구성·근거 판단·답변 프롬프트 관리 |
| `llm.with_structured_output(Schema)` | 분류·근거 판단 결과를 Pydantic 등 명시적 스키마로 수신 |
| `RunnableLambda` | 검증된 기존 함수를 체인에 연결 |
| `RunnableBranch` | 정해진 분류 결과에 따라 안내·확인·그래프 실행 선택 |
| `ainvoke()` | 비동기 실행 |

구조화 출력은 형식을 검증하는 도구이며 판단 내용의 정확성은 보장하지 않는다.
모델이 지원하는 출력 방식을 확인하고, 파싱·검증 실패를 인사나 근거 없음으로
조용히 바꾸지 않는다. 초기 버전에서는 구분 가능한 오류로 반환하고 평가에 기록한다.

입력 분석 스키마 초안:

```json
{
  "intent": "document_question",
  "standalone_question": "이력에서 확인한 대상을 반영한 독립 질문",
  "clarification_question": null,
  "reason_code": "resolvable_document_question"
}
```

`intent`는 `greeting`, `clarify`, `document_question`, `out_of_scope`로 제한한다.
값별로 필수·금지 필드를 검증한다. 분류 모델의 확신도 숫자를 사실상의 확률로 사용하지 않는다.
후속 질문의 대상을 복원할 때 이력에 없는 직군·날짜·버전·조건을 만들어 넣지 않는다.

바깥 체인의 개념은 `입력 분석 → 결과 검증 → RunnableBranch`다.
문서 경로에서만 컴파일된 LangGraph를 `ainvoke()`한다.

## 5. LangGraph 상태 설계

요청별 `StateGraph` 상태를 명시한다. 저장소·모델 같은 실행 의존성은 노드 클로저나
실행 컨텍스트로 전달하고 직렬화할 상태에 무조건 넣지 않는다.

| 상태 필드 | 의미 |
|---|---|
| `original_question` | 수정하지 않는 사용자 원질문 |
| `standalone_question` | 이력을 반영한 질문. 원질문의 요구를 유지 |
| `search_query` | 이번 검색에 사용할 표현 |
| `previous_queries` | 이미 실행한 질의 목록 |
| `search_count` | 실제 검색 시도 횟수 |
| `retry_count` | 최초 검색 이후 실행한 재검색 횟수 |
| `current_documents` | 이번 검색의 후보 문서·원시 점수 |
| `messages`, `sources` | 예산 안에서 실제 생성에 사용할 메시지와 근거 |
| `previous_evidence_ids` | 이전 검색과 새 근거 여부 비교 |
| `evidence_decision` | 충분·부족·조건 불명확 판정 |
| `missing_information` | 질문에 필요하지만 근거에서 확인되지 않은 항목 |
| `clarification_question` | 사용자에게 필요한 추가 질문 |
| `answer`, `status` | 최종 응답 |
| `timings`, `usage`, `trace` | 단계별 지연·사용량·판정·종료 사유 |

현재 회차의 문서·메시지·출처·판정은 기본적으로 덮어쓴다. 이전 검색 기록은 별도 trace에
남긴다. 무조건 누적 reducer를 적용하면 오래되거나 중복된 근거가 계속 커질 수 있다.
초기 버전은 현재 회차 근거로 답하고, 여러 회차 근거를 합치는 정책은 후속 평가로 결정한다.

대화 이력은 호출자가 제공한 검증된 범위만 사용한다. 초기 버전은 요청 단위 상태로 시작한다.
서버 전역 리스트에 사용자 대화를 쌓지 않는다. 영속 대화가 필요해지면 별도로
checkpointer·세션 식별·사용자별 격리를 설계한다.

## 6. 그래프 노드와 전이

| 노드 | 수행 내용 | 다음 경로 |
|---|---|---|
| `prepare_query` | 원질문·복원 질문·주어진 메타데이터 조건으로 최초 검색 질의 준비 | `retrieve` |
| `retrieve` | 저장소 비동기 검색, 검색 횟수·질의·시간 기록 | `prepare_context` |
| `prepare_context` | 전체 청크 유지, 중복 정리, 입력 토큰 예산·출처 구성 | `assess_evidence` |
| `assess_evidence` | 실제 생성에 전달할 근거가 질문의 필요한 항목을 충족하는지 판단 | 조건 분기 |
| `rewrite_query` | 누락 정보에 초점을 맞춰 검색 표현 변경 | 변경 시 `retrieve`, 변화 없으면 `abstain` |
| `generate_answer` | 승인된 메시지·출처로 답변 생성 | `END` |
| `clarify` | 질문 해결에 필요한 사용자 조건 확인 | `END` |
| `abstain` | 근거 부족 안내와 종료 사유 반환 | `END` |

`assess_evidence`는 예산에 들어가지 않아 생성에서 빠진 자료를 근거로 충분하다고
판정해서는 안 된다. 생성 노드는 평가한 메시지를 그대로 사용하고 재검색하지 않는다.

그래프 구성은 `StateGraph`, `add_node`, `add_edge`, `add_conditional_edges`로
정의한 뒤 `compile()`하고 실행하는 방식으로 구현한다. 이 문서에는 전체 실행 코드를
복사하지 않고 상태·노드 계약을 먼저 확정한다.

## 7. 근거 충분성 판단

검색 결과가 있다는 사실이나 높은 점수만으로 답변 가능하다고 판단하지 않는다.
원질문·현재 근거·필요 항목을 함께 보고 다음을 확인한다.

- 질문의 핵심 항목이 근거에 있는가? 기간과 조건을 물었으면 둘 다 확인되는가?
- 적용 대상·문서 버전·조건이 질문과 맞는가?
- 자료 간 충돌이 있거나 사용자가 정해야 할 조건이 빠져 있는가?
- 판단에 인용한 ID가 실제 sources에 존재하는가?

구조화 판정 예시:

```json
{
  "decision": "insufficient",
  "supported_source_ids": ["S1"],
  "missing_information": ["신청 가능 기간"],
  "clarification_question": null,
  "reason_code": "missing_required_fact"
}
```

`decision`은 `sufficient`, `insufficient`, `clarify`로 제한한다.
충분한 답변 가능 근거를 평가하는 모델도 틀릴 수 있다. 확인 질문·유보를 무조건 성공으로
세지 않고 실제 데이터 평가에서 정답·근거·불필요한 재검색을 따로 측정한다.
반드시 필요한 사용자 조건만 질문하며, 문서 검색으로 알 수 있는 내용을 사용자에게 떠넘기지 않는다.

## 8. 재검색 정책

기본은 **최초 검색 1회 + 재검색 최대 1회**다. 설정상 최대 재검색 2회까지 허용한다.

| 설정 | 최대 총 검색 횟수 |
|---|---|
| `max_retries=0` | 1 |
| `max_retries=1` (기본) | 2 |
| `max_retries=2` | 3 |

재검색 경로에서는 다음을 적용한다.

1. 부족한 항목을 기준으로 질의를 다시 구성한다. 특정 평가 질문의 정답을 넣지 않는다.
2. 이미 실행한 것과 같은 질의면 재검색하지 않는다.
3. 재검색의 새 근거·요구 정보 충족 정도를 확인한다. 동일 근거이고 진전도 없으면 조기 종료한다.
4. 사용자 조건이 모호하면 재검색보다 확인 질문으로 종료한다.
5. 최대 횟수·전체 시간·모델 호출 및 토큰 예산에 도달하면 종료한다.

`retry_count`는 실제로 재검색을 시작할 때 증가시키고 `search_count = retry_count + 1`을
기본 불변식으로 검사한다(최초 검색이 수행된 경우). 같은 검색의 SDK 네트워크 재시도는
논리적 재검색과 구분해 계측한다. SDK 재시도가 전체 호출을 무한정 늘리지 않게 설정한다.

LangGraph의 `recursion_limit`은 노드 단계 제한이며 재검색 횟수와 같은 값이 아니다.
명시적인 검색 횟수 제한을 주 제어로 사용하고 그래프 단계 제한은 추가 보호로 둔다.

메타데이터 필터는 저장소 어댑터가 지원하는 방식으로 전달한다. 필수 적용 대상·버전 등
호출자가 확정한 조건을 재검색 과정에서 몰래 제거하지 않는다. 다른 조건이 필요하면
사용자 확인 또는 명시적 정책이 필요하다.

## 9. 응답 계약

외부 체인과 그래프는 공통 응답 구조로 정규화한다. 아래는 제안이며 기존 API에는 아직 적용하지 않았다.

```json
{
  "status": "clarification_needed",
  "answer": "어떤 제도의 신청 방법을 알고 싶으신가요?",
  "sources": [],
  "retrieved_count": 0,
  "search_count": 0,
  "retry_count": 0,
  "reason_code": "missing_subject"
}
```

| 상태 | 의미 |
|---|---|
| `answered` | 근거에 따른 답변 |
| `greeting` | 인사·사용 안내 |
| `clarification_needed` | 사용자의 추가 정보 필요 |
| `out_of_scope` | 확인된 지원 범위 밖 요청 |
| `no_evidence` | 제한된 검색으로 필요한 근거를 확보하지 못함 |
| `error` | 저장소·모델·형식·시간 제한 등 시스템 실패 |

`retrieved_count`는 마지막 검색의 후보 수로 정의하고 전체 검색 후보 수는 trace에
별도 기록한다. sources는 최종 답변 생성에 전달한 근거이며 실제 인용 목록과 구분한다.
인사·검증 실패에서는 검색 횟수가 0이다. 빈 입력은 API에서 4xx로 처리할 수 있고,
화면용 문구와 검증 오류의 변환은 연결부에서 담당한다.

저장소 장애·시간 초과를 ‘문서에 정보 없음’으로 응답하지 않는다.
내부 상세 trace와 외부 응답을 구분하고 외부에 API 키나 제공자 오류 원문을 노출하지 않는다.

## 10. 현재 코드에서 재사용할 부분과 수정할 경계

현재 `rag_agent.py`의 `retrieve_documents()`와 `build_context()`를 재사용한다.
현재 `answer_question()`은 검색부터 생성까지 묶여 있으므로, 그래프의 생성 노드에서
그대로 호출하면 이미 수행한 검색을 다시 할 수 있다.

구현 시에는 메시지를 받아 생성·응답 검증만 하는 내부 함수를 분리하고,
기존 `answer_question()`도 같은 함수를 사용하게 한다. 기존 호출 인터페이스와
오프라인 테스트를 유지해 회귀를 막는다.

제안 파일 구조(추가 구현 단계에서 확정):

```text
rag-code-template_ext/rag-service/
├── rag_agent.py        # 기존 기본 RAG와 공통 검색·컨텍스트·생성 기능
├── rag_router.py       # 입력 검증, LangChain 분류·분기, 공통 응답
├── rag_workflow.py     # LangGraph 상태·노드·전이·재검색 정책
├── tests/              # 기존 회귀 + 라우팅·그래프 경로 테스트
└── evaluation/         # 데이터별 검색·답변·분기 평가
```

요청마다 그래프를 다시 구성하지 않고 의존성을 주입해 컴파일한 실행 객체를 재사용하되
사용자 상태는 요청별로 분리한다. 기존 `/rag-query` 연결은 독립 구현 검증 후 수행한다.
새 엔드포인트가 꼭 필요한 것은 아니다.

## 11. 시간·토큰·취소와 음성 확장

- 기본 검증·인사 규칙은 가능한 한 모델 호출 없이 처리한다.
- 의도 분석·근거 확인·재구성은 LLM 호출이 추가되므로 단계별 지연과 토큰을 기록한다.
- 전체 제한 시간은 바깥 라우터부터 생성 종료까지 적용한다. 노드마다 시간을 새로 리셋하지 않는다.
- 검색 횟수뿐 아니라 전체 모델 호출 수·시도별 토큰 사용량도 제한하고 기록한다.
- 출력 사용량은 호출 후에 알 수 있으므로 호출 전 입력 계산·출력 한도 설정과 함께 사용한다.
- 클라이언트 취소를 전파하고 무조건 새 검색·생성을 시작하지 않는다. 동기 스레드는
  취소 후에도 실행될 수 있으므로 제공자 시간 제한을 함께 둔다.

전체 1~2초는 음성 상담의 목표이며 현 구조에서 보장할 수 없다. 라우팅·검증 호출이
추가되면 기존 단일 생성보다 지연될 수 있다. 초기에는 비스트리밍으로 품질·종료 조건을
검증하고, 이후 최종 답변 생성만 스트리밍한다. 검색 중간 판단을 사용자에게 답변처럼 읽지 않는다.
텍스트·화면 출처·음성으로 읽을 텍스트의 구분은 음성 연동 시 별도로 확정한다.

## 12. 단계별 구현 순서

1. **계약 확정:** 실제 데이터 입력·메타데이터·지원 범위와 상태·응답 스키마를 합의한다.
2. **공통 생성 분리:** 현재 기본 함수 동작을 유지하면서 검색과 생성의 재사용 경계를 정리한다.
3. **입력 라우터:** 빈 입력·인사·짧은 주제·모호함·후속 질문을 분류하고 경로를 테스트한다.
4. **단일 검색 그래프:** prepare → retrieve → context → assess → answer/clarify/abstain을 구현한다.
5. **재검색 추가:** 기본 1회, 설정 최대 2회와 무진전·중복 질의·시간 제한 종료를 구현한다.
6. **데이터별 평가:** 실제 대표 데이터에서 기본 RAG와 그래프를 비교한다.
7. **API 연결:** 기존 주소·화면 호환 정책에 맞춰 호출부와 응답 모델을 변경한다.
8. **음성 확장:** 스트리밍·요청 취소·대화 이력의 세션 관리를 연결한다.

현재 논문 평가의 90% 검색률을 새 데이터의 보장 수치로 사용하지 않는다.
top_k도 설정으로 유지하고 실제 데이터로 재평가한다. 당장은 기본값을 변경하지 않는다.

## 13. 검증 계획과 완료 기준

### 오프라인 경로 테스트

- 빈 입력에서는 분류·검색·생성이 호출되지 않음.
- 인사와 질문이 섞이면 질문을 버리지 않음.
- ‘연차?’ 같은 짧은 주제를 단순 길이로 거부하지 않음.
- 이력에서 대상을 복원하거나, 없으면 확인 질문 반환.
- 충분한 근거에서는 검색 1회로 종료.
- 부족한 근거에서는 변경된 질의로만 재검색.
- 재검색 최대 1/2회 설정에서 총 검색이 각각 최대 2/3회로 제한됨.
- 동일 질의·새 근거 없음·예산 초과에서 조기 종료.
- 자료 충돌·조건 불명확·빈 컨텍스트·분류 형식 오류·저장소 장애·취소를 구분.
- 생성에 전달한 근거와 판정에 사용한 근거·출처가 일치.
- 서로 다른 요청의 상태·대화 이력이 섞이지 않음.

### 실제 평가

고정된 질문 세트에서 기본 RAG와 그래프를 비교한다. 인사·모호한 입력·후속 질문과
답변 불가 질문도 포함한다. 문서별 기준은 별도로 보관한다.

측정 항목은 검색 Hit@k·필수 근거 충족, 근거 충실성·답변 정확도, 인용 유효성,
확인 질문의 필요성, 불필요한 재검색 비율, 근거 부족 유보, 호출 실패율,
단계별·전체 지연과 사용 토큰이다. LLM 판정 결과를 그대로 평가 정답으로 쓰지 않는다.

완료 기준은 ‘루프가 실행됨’이 아니라 **경로와 종료가 예측 가능하고 기본 RAG 대비
품질·지연·비용의 변화를 설명할 수 있음**이다. 독립 테스트 후 서버에 연결한다.
