- 서비스의 `rag_agent.py`, `rag_state.py`, `rag_router.py`, `rag_workflow.py`, `rag_session.py`, `session_memory.py`, `rag_api.py` 및 관련 테스트·평가 코드를 확인했다.

- 시작 시 `data/eval/`, `rag-code-template_ext/eval_retrieval.py`, `rag-docs/rag-improve/`가 미추적 상태였다. 모두 사용자 기존 변경이며 이번 작업에서 만든 것으로 취급하지 않았다.
- 외부 디렉터리의 데이터 파이프라인·음성 서버·실제 HTTP 라우트 구현은 리뷰하지 않았다. 개선 문서의 MRR/Hit 수치는 독립 재계산하지 않았다.
- `/tmp/skala_rag_review_repro.py`에 모의 모델 및 메모리 FAISS를 사용하는 일회성 재현 스크립트를 작성했다.

## 코드 리뷰 결과

### 1. [P2] 근거 평가가 선택한 출처가 생성 단계에서 사용 제한으로 연결되지 않음

- 위치: `rag_workflow.py:256`, `rag_workflow.py:277`, `rag_workflow.py:311`.
- `supported_source_ids`는 알려진 ID인지 검증하지만 State에 보존하지 않는다. 생성에는 평가 이전의 전체 messages/sources를 전달한다.
- 평가 모델이 S1만 지지 근거로 선택했는데 생성 모델이 S2를 인용한 답변을 반환하도록 모의했을 때 `status=answered`, 전체 출처 a/b 반환을 재현했다.
- 선택 목록에 없다는 것이 반드시 거짓 근거라는 뜻은 아니지만, 평가에서 채택하지 않은 문서를 근거로 답변을 완성해도 통과하는 구조다. 여러 규정의 비슷한 조문이 섞이는 개선 문서의 문제와 연결된다.
- 개선: 선택 출처 ID를 State에 보존하고 생성용 근거를 그 목록에 맞춰 재구성한다. ID를 재할당한다면 메시지·응답·세션 재전송의 ID 매핑을 함께 보존한다. 관련 보충 자료가 필요하면 평가 결과에 명시적으로 포함하도록 계약을 정한다.

### 2. [P2] 인용이 하나도 없는 답변도 정상 답변으로 통과함

- 위치: `rag_agent.py:217`.
- 존재하지 않는 ID만 검사하며 인용 목록이 빈 집합인 경우 부분집합 검사가 참이다.
- 실제 문맥이 본인 혼인 5일만 포함하도록 만들고 생성 결과를 인용 없는 '형제 결혼도 휴가 5일입니다.'로 고정했을 때 `answered`를 재현했다. 실제 모델이 항상 이런 답을 한다는 의미가 아니라 검증기의 허용 범위를 확인한 모의 테스트다.
- 개선: 문서 사실에 대한 answered 응답에는 유효한 인용을 요구하고, 중요 주장과 대상·조건·예외가 해당 인용에 의해 지지되는지 검증한다. ID 존재 여부만으로 의미적 근거 일치를 보장할 수는 없다.
- 인사·확인 질문·유보 응답까지 일률적으로 인용을 강제하는 방식은 피한다.

### 3. [P2] 생성 단계에서 유보한 답변도 answered로 저장됨

- 위치: `rag_workflow.py:311`, `rag_workflow.py:312`.
- 생성 결과가 공통 상수 `NO_EVIDENCE`와 같아도 무조건 `answered/evidence_sufficient`가 된다.
- 동일 문구를 반환하는 모의 생성기로 실행했을 때 `answered`와 전체 출처 목록 반환을 재현했다.
- 개선: 생성 결과를 answer/abstain 등 구조화된 계약으로 받고 유보일 때 `no_evidence`로 반환·저장한다. 단일 문구 비교만으로 다양한 표현의 유보를 판별하는 방식은 한계가 있다.
- 서비스 내부 결과에는 `handoff`가 없다. 디렉터리 밖 HTTP 어댑터의 handoff 변환은 이번 리뷰 범위 밖이며 수정 여부를 판단하지 않았다.

## 개선 문서 항목별 판단

### 1. 조문 번호 메타데이터 필터: 적절하나 예제보다 구현 범위가 큼

- 현재 `rag_agent.retrieve_documents()`는 query/k만 전달하므로 필터 인자와 검색 제약 State를 추가해야 한다.
- 조문 지정은 일반 의미 검색보다 명시적 문서·조항 식별을 우선하는 방향이 적절하다.
- 설치된 LangChain FAISS를 사용한 재현에서 대상 문서를 전체 유사도 순위 26위에 두었을 때 문서의 `filter` 예제 형태는 0건, `fetch_k=26`을 추가하면 1건이었다. 필터가 전체 인덱스에서의 정확 조회를 보장한다고 가정하면 안 된다.
- 작은 현재 코퍼스에서는 메타데이터에 의한 직접 조회 어댑터/별도 매핑을 고려하고, 벡터 필터 방식을 쓴다면 후보 수 확대와 누락 방지 테스트가 필요하다. 대규모 인덱스에서 매 요청 전체 순회는 피한다.
- 해석된 독립 질문에서 제약을 추출하고 재검색에서도 문서·조항 제약을 보존해야 한다. 단순 원문 정규식만 적용하면 '그럼 같은 조항은?' 같은 후속 질문에 적용되지 않는다.
- 복수 조항, 조항 표기 변형, 규정 별칭, 없는 조항, 규정명 없는 번호의 모호성을 명시적으로 처리한다. 모호할 때 임의로 한 규정을 정답으로 택하지 않는다.

### 2. 근거 없는 질문 방지: 우선순위가 높지만 프롬프트 수정만으로는 부족

- 현재 이미 평가 → 제한적 재검색 → no_evidence 경로와 배경지식으로 누락 사실을 보완하지 말라는 지침이 있다. 새 그래프를 추가할 필요는 없다.
- 기존 구조를 유지하며 위 세 코드 문제와 대상·조건·예외 검증을 보완하는 방향이 적절하다.
- '문장에 그대로 있을 때만'을 문자열 일치로 강제하면 동의어, 문맥 해소, Q06 같은 계산 가능한 질문을 과도하게 거절한다. '동일한 적용 대상·조건이 문서에서 지지되고, 명시적 규칙으로 도출할 수 있어야 한다'로 바꾸는 것을 권한다.
- 프롬프트에서 자유 텍스트 N/A를 반환시키지 말고 현행 EvidenceDecision의 insufficient/missing_information을 유지해야 한다.
- Q29~32에서는 no_evidence 유보를 확인하되, 이를 문서 밖 모든 질문을 out_of_scope로 분류하는 문제와 혼동하지 않는다. 규정에서 '없다'고 명시한 Q28 같은 답변 가능한 부정 답변과도 구분해야 한다.

### 3. top_k 5 이상: 실험 제안은 적절하나 근거 문장은 수정 필요

- `RagSettings.top_k`, `QueryRequest.top_k`, `retrieve_documents()` 기본값은 이미 5다. 서비스 기본값 수정은 중복이다.
- 문서가 예로 든 4위 정답은 k=4에도 포함된다. Hit@3과 Hit@5만으로 k=4 대비 k=5의 효과를 확정할 수 없다. Hit@4와 5위 정답 문항을 확인해야 한다.
- 음성 서버의 top_k 변경은 사용자 지정 리뷰 범위 밖이므로 해당 코드는 확인하거나 변경하지 않았다.
- 서비스 내부에서는 후보 검색 수와 생성 컨텍스트 개수를 분리하는 방안도 고려할 수 있다. k를 늘려도 build_context의 전체 청크 토큰 예산 때문에 추가 후보가 실제 근거에 들어가지 않을 수 있다.
- k=4/5/7 등을 같은 인덱스·모델·질문으로 비교해 최종 정답률, 유보 정밀도, 컨텍스트 근거 재현율, 지연·토큰을 함께 봐야 한다. 검색 개수 하한을 무조건 강제할 근거는 아직 부족하다.

### 4. 답변 품질 평가: 가장 먼저 기준선을 확보해야 함

- 검색 적중과 최종 답변 품질을 분리하자는 제안은 적절하다.
- 기존 `evaluation/run_evaluation.py:237`은 레거시 `rag_agent.answer_question()`을 호출한다. 이 경로만 평가하면 RagService의 근거 판정·재검색·기억 경로를 검증하지 못한다.
- `run_hr_session_evaluation.py`처럼 RagService 세션 경로를 대상으로 데이터셋 입력·사례별 추적을 확장하는 방향이 범위에 맞는다. HTTP handoff 계약 평가는 별도의 범위다.
- 단일 질문은 세션을 분리하고 후속 질문 사례는 같은 세션에서 평가한다. request_id 재전송은 별도 사례로 구분한다.
- 질문, 답변, 상태, 근거 판정, 검색별 query/후보, 생성에 포함된 출처, 실제 인용, 정답·유보 판정, 지연·토큰, 인덱스/코드/모델/프롬프트 설정을 기록한다. 실패·타임아웃도 전체 분모에 남긴다.
- Q06 계산, Q27 조문 지정, Q28 부정 규정, Q29~32 유보뿐 아니라 명확한 정상 질문을 과도하게 유보하는지 함께 본다. Judge 결과는 사람의 표본 검토와 별도로 표시한다.
- 데이터/모델의 MRR 개선 수치는 문서에 제시된 주장으로만 취급했다. '데이터 쪽 개선 완료'나 12개 holdout만으로 일반화 성능이 확정되었다고 결론 내릴 수 없다.

## 권장 진행 순서

1. 현행 RagService 기준선을 고정하고 주요 실패 문항의 회귀 사례를 만든다.
2. 생성 근거 제한, 인용 검증, 유보 상태의 일관성을 보완한다.
3. 조문 명시 질문의 검색 제약과 재검색 시 보존을 구현한다.
4. 같은 기준선에서 k와 컨텍스트 구성을 비교한다.
5. 임베딩 모델 변경은 인덱스와 모델의 일치를 확인하는 별도 데이터 파이프라인 작업으로 다룬다. 이번 코드 리뷰 범위에는 포함하지 않는다.
