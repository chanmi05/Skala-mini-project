# 인사규정 RAG 단계별 연결 결과

작업일: 2026-10-25 (Asia/Seoul), 브랜치: rag-preprocessing-integration.

## 1. 데이터 점검

규정 PDF 5종은 모두 텍스트 추출·fixed/article 청킹이 가능했다. 현재 코드의 fixed 결과는 113개, article 결과는 96개이며 기존 저장 인덱스는 115개·1536차원이다. 차이를 숨기거나 원본을 자동 재생성하지 않았다. 휴가규정 2쪽을 렌더링해 본문 추출 순서를 표본 대조했다.

## 2. API·세션 연결

기존 uvicorn 모듈을 유지한 채 rag_api.create_app으로 연결했다. /sessions, /rag-query, /upload-paper를 제공하며 response/answer/output 호환 필드와 문서·페이지·조항 출처를 반환한다. 브라우저·음성 프록시의 세션 소유권을 구분하고, 같은 세션·초기 요청의 재전송 중복을 방지한다. top_k별 서비스도 같은 SessionCoordinator를 사용한다.

API 응답에는 청크 원문·프롬프트·내부 trace를 넣지 않는다. 등록 문서에 초안/회사 미확정 표시가 있거나 요약이 실패하면 확인 상태와 warning을 반환한다.

## 3. 업로드·검색 갱신

같은 파일명은 해당 문서의 청크만 교체하고 다른 문서를 유지한다. 기존 인덱스를 복제해 처리한 뒤 별도 디렉터리에 저장을 완성하고 새 스냅샷으로 교체한다. 파싱·임베딩·저장 실패 시 원본을 유지하는 테스트를 추가했다. 업로드 중 질의는 시작 시점의 스냅샷을 사용한다. 교체 후 이전 대화는 409로 새 대화 시작을 안내한다.

CLI도 기존 인덱스를 먼저 삭제하지 않으며 --output-dir로 별도 적재할 수 있다.

## 4. 실제 OpenAI 평가

기존 설정인 GPT-4o와 text-embedding-ada-002를 사용했다. API 인증·모델 접근을 확인한 후 실행했으며 키 값은 출력·기록하지 않았다.

실제 모델에서 판정 필드의 잘못된 조합이 발생해, MemoryDecisionOutput의 분기별 중첩 union과 모든 구조화 호출의 strict schema를 적용했다. 요약 존재 여부도 기억 노드에 전달하고, 새로운 명시적 문서 질문과 과거 대화 참조를 구분하도록 지침을 보완했다.

추가 브라우저 반복에서 제어에 사용하지 않는 reason_code가 빈 문자열일 때 전체 판정이 거부되는 문제도 확인했다. 새 분류·기억 wire schema에서는 이 필드를 제거하고 코드가 제어 사유를 만든다. 레거시 설명 필드의 빈 값도 허용하되 질문·분기·출처에 필요한 검증은 유지했다. 해당 회귀 테스트를 추가하고 아래 최종 평가를 다시 수행했다.

- [최종 세션 평가](../rag-code-template_ext/rag-service/evaluation/runs/hr_session_20261025T105257260569Z/report.md): 9개 사례의 기대 상태 9/9 일치. 지정한 정답 표현과 출처 조건도 충족했고 과거 참조에서 요약 조회를 확인했다. 이 결과는 정확도 100%를 의미하지 않는다.
- 같은 실행의 모델 호출은 34회, 제공자 입력 토큰 합계는 41,889개다. 전체 9개 사례의 응답 지연 중앙값은 약 3.72초이며 인사·요약 갱신을 포함한다. STT/TTS·전체 화면 전달은 포함하지 않았다.
- 개발 중 세션 실행 7회를 보존했다. 초기 실패·불필요한 확인 질문·과거 참조 실패가 있는 결과도 삭제하지 않았다. 위 최종 실행만을 최종 코드의 대표 소규모 세션 결과로 지정한다.
- [최종 실제 API 업로드 평가](../rag-code-template_ext/rag-service/evaluation/runs/hr_api_20261025T105257588628Z/report.md): 실제 임베딩 업로드와 실제 LLM 질의·후속 질문·대화 종료를 임시 인덱스에서 확인했다. 이전 대화 409, 종료 대화 404를 포함한 7개 HTTP 단계가 기대대로 동작했다. 원본 인덱스 해시는 동일했다.

이 질문들은 개발 보완에 사용한 고정 샘플이다. 독립된 평가 데이터·사람의 전면 채점·법률 적합성 확인은 수행하지 않았다.

## 5. 화면·회귀 검증

- RAG/세션/HTTP/업로드: 오프라인 테스트 94개 통과.
- 음성 게이트웨이: 41개 통과. 실제 FFmpeg 변환·정리는 검증용 바이너리로 수행하고 STT·TTS 모델 호출은 모의했다. 새 테스트는 음성 텍스트 API → RAG API → FAISS → 세션 종료 흐름을 검증한다.
- Vue 프론트: Node 24.22.1에서 38개 통과. 후속 질문의 session_id 유지, 요청 ID 재사용, 새 대화 종료, 문서 변경 충돌 초기화를 포함한다.
- Vue 프로덕션 빌드 성공.
- 브라우저에서 실제 RAG 콘솔 질문·후속 질문, 검색 수·답변·문서/조항/페이지 표시와 새 대화를 확인했다. 최신 화면 증거는 [콘솔 화면](../rag-code-template_ext/rag-service/evaluation/inspections/hr_20261025/console.png)에 저장했다.

## 남은 제약

- Gradle 인증 테스트는 --no-daemon 재실행에서도 Unable to establish loopback connection으로 테스트 실행 전에 실패했다. Java 인증 테스트를 통과했다고 판단하지 않는다.
- 현재 workplace/.env의 JWT_SECRET과 DB 실행 환경이 준비되지 않아 실제 로그인 → Vue → 음성 서버 → RAG의 전체 서버 기동은 검증하지 않았다. 이 구간의 API 형식·세션 전달·JWT 거부 동작은 모의/계약 테스트와 분리한다.
- RAG 단독 API는 로컬 공개 API이며, 소유권 쿠키/전달된 Authorization을 구분할 뿐 JWT를 자체 검증하지 않는다. 배포용 인증·업로드 권한·공유 세션/다중 워커는 별도 작업이다.
- OCR·전체 표 복원·시행일/적용 대상 필터·다른 이름의 개정본 판별·session_facts 자동 저장은 미구현이다.
- API·콘솔 실행과 설정은 [API 사용법](HR_RAG_API_USAGE.md), 작업 내용과 실패 기록은 [작업 로그](작업기록/2026-10-25_011_인사규정_RAG_단계별_연결_및_검증.md)에 정리했다.
