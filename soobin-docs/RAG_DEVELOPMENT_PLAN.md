# RAG 개발 방향 및 논의 기록

작성일: 2026-10-23 (Asia/Seoul)  
작업 브랜치: `dev-rag`

구현 진행: 이후 `rag_agent.py`와 오프라인 테스트를 추가했다. 기존 API는 변경하지 않았다.
아래는 최초 논의 기록이며, 현재 구현·검증 범위는 [독립 RAG 모듈 사용법](RAG_AGENT_USAGE.md)을 참고한다.
실제 저장소·OpenAI 연결 평가도 24개 수행했다. [최초 평가 결과](RAG_BASELINE_EVALUATION.md)에 기록했다.

## 1. 현재 어디까지 논의했는가

현재 프로젝트의 RAG 동작과 코드를 확인했고, **전처리·청킹과 독립적인 Python 모듈로
검색·컨텍스트 구성·답변 생성을 개발하는 방향**까지 논의했다.

`rag_agent.py`라는 별도 파일에 RAG 함수를 두고 기존 `/rag-query` API에서 호출하는
구조를 제안했다. 아직 이 모듈을 구현하거나 기존 API를 변경하지는 않았다.
함수명과 입력·출력 형식도 아래 제안을 바탕으로 구현 시 확정해야 한다.

## 2. 담당 범위

### 확정된 범위

- 원본 데이터 수집, HWP/PDF 추출, 전처리와 청킹은 다른 담당자의 책임이다.
- 이번 개발은 RAG의 검색, 컨텍스트 구성, LLM 답변 생성, 출처 반환에 집중한다.
- 작업 폴더는 `rag-code-template_ext/`를 중심으로 한다.
- Java 인증 서버(`workplace`)와 음성 서버(`voice-ai_code`)의 변경은 현재 범위에 포함하지 않는다.

### 연동 담당자와 확인할 경계

임베딩과 벡터 DB 적재 책임은 아직 확정하지 않았다. 다음 두 경우를 구분한다.

| 다른 담당자의 제공 결과 | RAG 쪽에서 연결할 지점 |
|---|---|
| 청킹 완료 데이터 + 메타데이터 | 입력 검증, 임베딩·적재를 별도 색인 모듈에서 수행한 뒤 검색 |
| 적재된 벡터 저장소 또는 검색 인터페이스 | 저장소에 연결해 검색부터 수행 |

우선 기존 FAISS 저장소를 주입해 RAG 함수를 개발하면 이 합의가 완료되기 전에도
검색·답변 로직을 구현할 수 있다. 질의마다 원문을 다시 청킹하거나 색인하지 않는다.

## 3. 현재 코드 및 검증 상태

주요 백엔드 파일은 `rag-code-template_ext/rag_external-web_pdf_closed_llm.py`다.
API, 자료 등록, 임베딩, 저장소 로딩, 검색, 답변 생성이 한 파일에 모여 있다.

| 항목 | 현재 상태 |
|---|---|
| `/upload-paper` | PDF 추출·청킹·임베딩·FAISS 저장 |
| `/upload-topic` | 네이버 뉴스 제목·요약 수집·청킹·임베딩·FAISS 저장 |
| `/rag-query` | `pdf` 또는 `web` 저장소 검색 후 GPT-4o로 답변 생성 |
| 벡터 저장소 | 로컬 FAISS, `faiss_db/pdf`와 `faiss_db/web` |
| 질의 응답 형식 | `prompt`, `response` |
| 화면 | RAG 폴더와 저장소 루트에 `external_index.html`이 각각 존재 |

2026-10-23에 확인한 내용:

- Python 3.11 가상환경에 기존 requirements 설치 및 의존성 검사 통과.
- RAG 서버 기동, API 문서, 입력 검증, CORS 응답 확인.
- 기존 PDF 저장소의 `paper-attention.pdf` 확인: 「Attention Is All You Need」, 44개 청크.
- Transformer 구조에 관한 테스트 질문에서 5개 청크 검색과 한국어 답변 반환 성공.
- 해당 API 테스트는 HTTP 200, 약 5.7초 소요. 단일 기능 테스트이며 품질 평가 결과는 아니다.
- 새 PDF 업로드와 뉴스 수집의 실제 외부 연동은 아직 검증하지 않았다.

당시 로컬 실행 주소는 백엔드 `http://127.0.0.1:8001`, 화면
`http://127.0.0.1:5174/external_index.html`이었다. 프로세스 실행 상태는 사용 시 다시 확인한다.
화면은 HTML만 복사한 임시 디렉터리에서 제공했으므로, 소스 HTML을 수정하면
해당 복사본도 갱신해야 반영된다. 이 방식은 개발용 임시 실행 방식이다.

## 4. 제안한 모듈 구조

```text
기존 /rag-query API
    │ 요청 검증·저장소와 LLM 선택
    ↓
rag_agent.py
    │ 질문 → 검색 → 컨텍스트 구성 → LLM 호출 → 결과 정리
    ↓
답변 + 검색 근거·출처
    ↓
API 응답 → 화면
```

제안 파일 위치:

```text
rag-code-template_ext/
├── rag_external-web_pdf_closed_llm.py  # 기존 API 연결부
├── rag_agent.py                       # 새 검색·답변 모듈
└── tests/                             # 검색·답변 로직 검증
```

함수 인터페이스의 초안:

```python
async def answer_question(
    question: str,
    vectorstore,
    llm,
    top_k: int = 5,
) -> dict:
    ...
    return {
        "answer": answer,
        "sources": sources,
    }
```

이 함수는 저장소와 LLM을 외부에서 전달받는다. FastAPI 요청 객체, 업로드 파일,
원본 문서 파서, 전역 저장소 변수에 직접 의존하지 않도록 한다.
별도 파일을 import하는 것만으로 서버 실행·외부 API 호출·색인이 발생하지 않게 한다.
현재 기능에는 자율적인 도구 선택이나 Agent 프레임워크가 필요하지 않다.

## 5. 새 모듈의 수행 과정

1. **입력 검증**: 빈 질문 거부, `top_k`의 하한·상한 확인.
2. **검색**: 전달받은 저장소에서 질문과 관련된 청크와 메타데이터 조회.
3. **컨텍스트 구성**: 중복을 정리하고 길이 예산 안에서 출처 식별자와 본문 구성.
4. **답변 생성**: 검색 근거와 질문을 LLM에 전달하고 근거가 부족한 경우의 응답 처리.
5. **결과 반환**: 답변과 실제 사용한 근거를 추적할 수 있는 출처 반환.

검색 건수와 실제 컨텍스트에 사용한 건수는 다를 수 있다. `hits`와 `sources`를 모두
사용한다면 의미를 구분하고, 화면의 건수가 어느 쪽을 나타내는지 명시한다.
출처 번호는 컨텍스트와 응답에서 동일하게 유지하고, 파일명·조항·페이지 등의
값은 제공된 메타데이터만 사용한다. 없는 값은 생성하지 않는다.

비동기 API에서 이벤트 루프가 막히지 않도록 비동기 검색·LLM 호출을 사용하거나
동기 작업을 스레드로 분리한다. 구체적인 저장소 어댑터와 오류·시간 제한 정책은 구현 시 정한다.

## 6. 기존 업로드 API의 취급

`/upload-paper`, `/upload-topic`의 수집·전처리·청킹 로직을 이번 작업에서 고치지 않는다.
기존 동작 확인용으로 유지할 수 있다. 새 RAG 모듈은 두 API를 호출하지 않는다.

두 API에는 임베딩·적재도 포함되어 있지만 이를 곧바로 새 RAG 함수에 옮기지는 않는다.
임베딩·적재가 본인 책임으로 정해지면 별도 색인 계층에서 처리한다.
검색·답변 함수와 데이터 갱신 작업의 수명주기를 분리한다.

## 7. 코드 리뷰에서 확인한 사항

| 우선순위 | 문제 | 재현 또는 확인 내용 | 이번 작업과의 관계 |
|---|---|---|---|
| P1 | async API 내부 동기 검색·LLM 호출 | 모의 LLM 지연으로 이벤트 루프 지연 확인 | 새 모듈에서 해결 |
| P1 | 업로드마다 저장소 전체 교체 | 기존 저장소에 추가하지 않고 새 인스턴스 생성 | 적재 담당과 정책 합의 |
| P1 | 저장 실패 전에 활성 메모리 저장소 변경 | 모의 저장 실패 후에도 활성 저장소가 바뀜 | 적재 담당과 수정 범위 합의 |
| P2 | 응답과 화면 필드 불일치 | API는 `response`, 화면은 `answer`·`output`·`hits` 사용 | API 어댑터·화면 계약 정리 |
| P2 | `top_k` 1~4를 무시 | `top_k=1`이 실제 검색에 5로 전달됨 | 새 모듈에서 해결 |
| P2 | 저장소 경로가 실행 위치에 의존 | 다른 작업 디렉터리에서 기존 저장소 미인식 | 기존 연결부의 경로 정리 |
| P2 | 한국어 웹 질문을 같은 문자열로 두 번 검색 | 번역 없이 동일 질의 2회 호출 확인 | 새 검색 로직에서 중복 방지 |

화면의 `Hit count: 0`은 실제 검색 실패를 뜻하지 않았다. API가 `hits`를 반환하지
않는데 화면에서 빈 배열로 처리한 결과였다. 답변이 JSON 전체로 표시되는 것도
필드 불일치 때문이다.

## 8. 구현 전 합의할 입력·출력 계약

- 청크 본문과 청크 ID, 문서 ID의 제공 형식.
- 적용 대상, 장·조 제목, 파일명 등 메타데이터의 필드명과 누락 허용 범위.
- 임베딩 모델·차원·저장소 정보와 임베딩·적재 담당 범위.
- 검색 필터에 필요한 필드와 필터 미지정 시 동작.
- 응답 필드명 및 검색 결과·출처·검색 건수의 의미.
- 기존 `prompt/response` 응답을 유지할지, 화면과 함께 변경할지.

API 호환성을 유지해야 한다면 새 함수의 `answer`를 기존 API의 `response`에 매핑하고
출처·검색 건수를 확장할 수 있다. 최종 응답 스키마는 아직 확정되지 않았다.

## 9. 다음 작업 순서와 완료 기준

1. 기존 저장소로 동작하는 최소 `rag_agent.py` 인터페이스와 응답 계약을 확정한다.
2. 검색·컨텍스트·답변 생성을 모듈로 구현한다. 원본 수집·청킹 코드는 건드리지 않는다.
3. 가짜 저장소·가짜 LLM으로 빈 결과, `top_k`, 출처 매핑, 오류 처리를 검증한다.
4. `/rag-query`에서 새 함수를 호출하도록 연결하고 화면 응답 필드를 맞춘다.
5. 기존 논문으로 실제 통합 테스트를 수행하고 대표 질문·근거 부족 질문을 평가한다.
6. 연동 계약이 정해지면 실제 전달 데이터 또는 저장소로 교체한다.

완료 기준은 별도 모듈에서 검색·답변이 동작하고, 입력부터 출처까지 추적 가능하며,
API·화면과 응답 계약이 일치하는 것이다. 한 질문에 답변이 나오는 것과 검색·답변
품질이 검증되는 것은 구분한다.

현재는 **현황 확인·실제 질의 테스트·코드 리뷰·모듈 분리 방향 논의 및 문서화까지 완료**했다.
새 모듈 구현과 API 변경은 다음 작업이다.
