# RAG 질의 함수의 문제점과 해결 전략

작성일: 2026-10-23 (Asia/Seoul)

## 1. 범위와 개발 원칙

검토 대상은 기존 서버의 `rag_query()`와 이 함수에 연결된 요청·응답 모델이다.
데이터 수집, 문서 추출, 전처리, 청킹, 임베딩 적재, 저장소 갱신은 이 문서의 개선 범위에서 제외한다.
앞으로는 웹 검색 없이 PDF에서 만들어진 문서 저장소만 사용한다.

기존 동작은 보존하고, 검색·컨텍스트·답변 로직을 `rag_agent.py`에 독립적으로 개발한다.
검증 후 기존 `/rag-query`가 새 함수를 호출하도록 연결한다.
같은 URL을 중복 등록하거나 함수 오버라이드를 사용하지 않는다.

현재 논문을 대상으로 검색·LLM 답변 생성은 성공했다. 아래 항목은 기본 동작 실패가 아니라
입력 처리, 동시 요청, 근거 추적과 개발 구조를 보완하기 위한 사항이다.

## 2. 문제점과 해결 방법

### 2.1 동기 호출로 다른 요청이 지연될 수 있음

**현재 코드:** `async def rag_query()` 안에서 `similarity_search_with_score()`와
`llm.invoke()`를 동기로 호출한다. PDF 분기의 검색은 기존 서버 파일 348행,
LLM 호출은 385행에 있다.

**영향:** 단일 워커에서 외부 응답을 기다리는 동안 이벤트 루프가 막혀 다른 요청도
지연될 수 있다. 이전 모의 테스트에서 동기 LLM 지연이 다른 코루틴을 지연시키는 현상을 확인했다.

**해결 전략:**

- 검색과 LLM의 비동기 인터페이스를 사용한다.
- 동기 인터페이스만 제공된다면 해당 작업을 스레드로 분리한다.
- 단순히 함수에 `async`를 붙이는 것으로 해결되었다고 판단하지 않는다.

**완료 기준:** 느린 검색·LLM을 모의 실행해도 독립된 코루틴이 함께 지연되지 않는다.

### 2.2 요청한 검색 개수를 무시함

**현재 코드:** 341행의 `max(5, (rag_request.top_k or 5))` 때문에 1~4를 요청해도
5개를 검색한다. `top_k=1`이 실제 검색 호출에 5로 전달되는 것을 확인했다.

**해결 전략:** 검증된 `top_k`를 그대로 사용한다. 생략 시에만 기본값 5를 적용한다.
하한 1과 상한을 API와 독립 함수에서 동일하게 관리한다. 상한 50은 초기 제안이며
검색·비용·지연 평가 후 확정한다.

**완료 기준:** `top_k=1`이 저장소 호출에 1로 전달되고, 범위 밖 입력은 검색 전에 거부된다.
저장소에 문서가 부족하면 실제 반환 건수는 요청값보다 작을 수 있다.

### 2.3 답변의 검색 근거와 출처를 반환하지 않음

**현재 코드:** `AnswerResponse`는 `prompt`, `response`만 정의한다. 검색 점수와
청크 메타데이터는 응답에 포함되지 않고, 컨텍스트에도 실제 파일명·조항 등이 연결되지 않는다.

**영향:** 답변의 근거를 추적하거나 검색 결과를 평가하기 어렵다. 화면은 `hits`를
기대하므로 실제 검색 성공과 무관하게 `Hit count: 0`을 표시한다.

**해결 전략:**

- 검색 건수와 컨텍스트에 사용한 근거 목록을 구분해 반환한다.
- 근거마다 출처 ID를 부여하고 청크 ID·문서 ID·제공된 메타데이터를 유지한다.
- 컨텍스트의 출처 ID와 반환 목록의 ID를 일치시킨다.
- 거리값은 확률이나 신뢰도로 표시하지 않는다. 점수의 의미를 명시한다.
- LLM에 전달한 근거 목록과 LLM이 실제 인용한 목록을 구분한다.
- 없는 페이지 번호·조항·문서 ID를 LLM으로 추정하지 않는다.

**완료 기준:** 사용자가 답변에 제공된 근거를 식별할 수 있고, 화면 건수와 API의 의미가 일치한다.
출처를 제공한다는 사실만으로 답변이 근거에 부합한다고 판정하지는 않는다.

### 2.4 컨텍스트 구성 시 근거가 중간에 잘릴 수 있음

**현재 코드:** 358~369행에서 최대 12,000자를 기준으로 `content[:remaining]`을
사용한다. 마지막 청크의 문장·조건·예외가 잘릴 수 있으며, 제목·질문·지시문 길이는
이 본문 예산에 포함되지 않는다.

**해결 전략:**

- 검색 순서를 유지하면서 청크 단위로 컨텍스트에 포함한다.
- 남은 예산에 들어가지 않는 청크는 제외하는 것을 기본 정책으로 한다.
- 큰 청크 하나 때문에 모든 근거가 제외되는 경우를 감지하고 명시적으로 처리한다.
- 질문·지시문·출처 표시와 응답 여유를 고려한 토큰 예산을 설정한다.
- 중복 제거는 청크 ID를 우선 사용한다. 본문이 같아도 출처나 적용 대상이 다르면
  무조건 하나로 합치지 않는다.
- 원본 청크를 다시 청킹하지 않는다. 입력 크기 계약의 문제는 데이터 담당자와 조정한다.

**완료 기준:** 컨텍스트 예산을 초과하지 않고, 포함된 근거가 원문 청크와 일치한다.
제외된 청크는 답변에 사용한 출처 목록에 넣지 않는다.

### 2.5 질문과 검색 개수의 입력 검증이 부족함

**현재 코드:** `prompt`는 문자열 타입만 확인하므로 빈 문자열·공백 질문을 허용한다.
`top_k`는 요청 모델에서 하한만 확인한다. 화면의 입력 제한은 API 직접 호출을 막지 못한다.

**해결 전략:**

- 질문 앞뒤 공백을 제거하고 비어 있으면 거부한다.
- 질문 최대 길이와 `top_k` 범위를 정한다.
- 독립 함수를 직접 호출할 때도 같은 계약이 적용되도록 검증한다.
- 함수의 검증 오류는 API 연결부에서 적절한 4xx 응답으로 변환한다.

**완료 기준:** 잘못된 입력에서 검색과 LLM 호출이 발생하지 않는다.

### 2.6 현재 요구에 불필요한 웹 분기가 섞여 있음

**현재 코드:** `rag_query()`가 웹/PDF 저장소 선택, 서로 다른 프롬프트,
웹 질의 번역 후보 처리 등을 함께 수행한다. 한국어 웹 검색은 실제 번역 없이
같은 질문을 두 번 조회한다.

**해결 전략:** 새 모듈은 `source` 없이 전달받은 문서 저장소만 검색한다.
기존 API와 화면의 호환성을 위해 `source="pdf"`는 연결부에서 당분간 유지할 수 있다.
API 전체에서 웹 지원을 제거하는 작업과 독립 모듈 개발은 분리한다.
웹 요청을 PDF 저장소로 조용히 바꿔 처리하지 않는다.

**완료 기준:** 새 모듈에 네이버·웹 수집·PDF 파서 의존성이 없고, 한 질문에 의도한 검색만 수행한다.

## 3. 추가로 설계할 동작

다음은 확정된 장애라기보다 새 모듈에서 명확하게 정해야 할 정책이다.

| 상황 | 처리 방향 |
|---|---|
| 검색 결과 없음 | 근거 없음 상태 반환, LLM 호출 생략 |
| 결과는 있지만 유효한 컨텍스트 없음 | 근거 없음 또는 입력 크기 문제를 구분해 반환 |
| 질문과 관련성이 부족한 결과 | 평가 질문으로 탐지 품질을 확인하고 필요 시 관련성 판단 추가 |
| 검색 실패·LLM 실패·시간 초과 | 내부에서 구분하고 API에서 일관된 오류로 매핑 |
| 근거에 없는 질문 | 답변 불가 또는 근거 부족을 명시하도록 지시하고 평가 |
| 검색 자료에 지시문 포함 | 답변 지시와 참고 자료를 구분하고 자료의 명령을 따르지 않도록 구성 |
| 잘못된 출처 ID를 인용 | 반환 근거와 대조하고 검증 실패 정책 적용 |

현재 코드에도 빈 검색 결과와 빈 컨텍스트 처리는 있다. 이를 새 모듈에서 유지·검증한다.
반면 관련 없는 질문에도 벡터 검색은 결과를 반환할 수 있으므로 결과가 있다는 사실을
충분한 근거로 간주하지 않는다. 고정 거리 임계값은 점수 체계와 평가 없이 도입하지 않는다.
근거 부족 응답이나 인용을 프롬프트에 적는 것만으로 품질이 보장되지는 않는다.

## 4. 모듈과 API의 책임 분리

```text
기존 /rag-query
    ├─ 요청 검증 및 저장소·LLM 전달
    ↓
rag_agent.py의 answer_question()
    ├─ 입력 계약 확인
    ├─ 관련 청크 검색
    ├─ 컨텍스트·출처 구성
    ├─ LLM 답변 생성
    └─ 답변·근거 반환
    ↓
기존 API의 응답 모델에 매핑
```

단일 `rag_agent.py` 안에 `retrieve_documents()`, `build_context()`,
`answer_question()`을 정의하는 구성으로 시작한다. 저장소와 LLM은 인자로 전달받고
서버의 전역변수나 FastAPI 객체를 직접 참조하지 않는다. LangGraph 도입은 현재 필요하지 않다.

함수 인터페이스와 반환 형태의 초안은 다음과 같다. 아직 구현된 코드는 아니다.

```python
async def answer_question(question, vectorstore, llm, top_k=5) -> dict:
    ...
    return {
        "answer": answer,
        "retrieved_count": retrieved_count,
        "sources": sources,
    }
```

- `retrieved_count`: 저장소가 반환한 후보 수.
- `sources`: 실제 컨텍스트에 포함한 근거 목록. 전부가 답변에서 인용되었다는 의미는 아니다.
- `answer`: 답변 또는 근거 부족 안내.

기존 API의 `response` 필드를 유지하려면 `result["answer"]`를 매핑하고, 검색 건수와
출처 필드를 응답 모델에 추가한다. 모델을 변경하지 않고 필드만 반환하면 응답 모델에서
제외될 수 있으므로 모델과 화면을 함께 맞춘다. 최종 필드명은 연결 전에 확정한다.

## 5. 구현·검증 순서

1. 입력 범위, 응답 필드, 출처와 검색 건수의 의미를 확정한다.
2. 독립 `rag_agent.py`에 검색·컨텍스트·답변 함수를 구현한다.
3. 가짜 저장소·LLM으로 입력 오류, `top_k`, 빈 결과, 출처 연결, 길이 예산,
   실패·시간 초과와 동시 요청 처리를 검증한다.
4. 기존 논문 저장소로 정상 질문과 근거 부족 질문을 평가한다.
5. 기존 `rag_query()`를 새 함수 호출로 연결하고 API·화면 필드를 맞춘다.

기존 함수는 모듈 검증이 끝난 뒤 변경한다. `/upload-paper`와 `/upload-topic`의
전처리·적재 코드는 이번 개선 작업에서 수정하지 않는다.

## 6. 완료 조건

- 기존 논문으로 실제 검색·답변이 정상 동작한다.
- 빈 질문과 범위 밖 `top_k`는 검색 전에 거부된다.
- 요청한 검색 개수가 저장소에 그대로 전달된다.
- 검색 건수와 컨텍스트에 포함된 출처가 구분되어 추적된다.
- 근거가 예산에 맞게 보존되며 빈 근거에서 불필요한 LLM 호출이 없다.
- 느린 호출이 이벤트 루프를 직접 막지 않는다.
- 기존 `/rag-query` 주소와 연결 화면이 합의한 응답 형식으로 동작한다.

관련 논의와 담당 경계는 [RAG 개발 방향 및 논의 기록](RAG_DEVELOPMENT_PLAN.md)을 참고한다.
이 문서는 개선 계획이며, 새 모듈 구현이나 기존 함수 수정이 완료되었다는 의미는 아니다.
